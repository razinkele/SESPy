# Direction bug fix report — dynamics simulation

## Summary

`isa_to_numeric_matrix` documents `M[i, j]` as edge i->j (row=source,
col=target). `simulate_dynamics` computes `x_{t+1} = M @ x_t`, i.e.
`x_{t+1}[i] = sum_j M[i,j] * x_t[j]` — a node's next state depends on the
nodes it points AT, not the nodes pointing at it. Influence propagated
backwards along edges.

Fix: added `isa_to_dynamics_matrix(isa)` to `sespy/dynamics.py`, which
delegates to `isa_to_numeric_matrix` and returns its transpose — oriented so
`x_{t+1} = A @ x_t` propagates along edge directions. Pointed
`analysis_simulation._build_matrix()` at the new function. This single change
fixes both `_run_sim` (calls `simulate_dynamics`) and `_run_mc` (calls
`state_shift_monte_carlo`), since both go through `_build_matrix()`.

`simulate_dynamics` itself, `isa_to_numeric_matrix`'s orientation,
`create_boolean_rules`, `boolean_attractors`, `analysis_boolean.py`,
`laplacian_eigenvalues`/`laplacian_stability` were NOT touched, per
instructions.

## Files changed

- `sespy/dynamics.py` — added `isa_to_dynamics_matrix()` (new function,
  after `isa_to_numeric_matrix`).
- `sespy/modules/analysis_simulation.py` — `_build_matrix()` now calls
  `dynamics.isa_to_dynamics_matrix(isa)` instead of
  `dynamics.isa_to_numeric_matrix(isa)`.
- `tests/test_dynamics.py` — three new tests (see below).

Confirmed both `_run_sim` and `_run_mc` in `analysis_simulation.py` call
`_build_matrix()` (lines 123 and 142) — no other matrix-build call site in
that module.

`sespy/modules/analysis_boolean.py:98` still calls
`dynamics.isa_to_numeric_matrix(isa)` directly — correct, untouched, as that
path needs row=source/col=target for `create_boolean_rules`.

## Tests added (tests/test_dynamics.py)

1. `test_isa_to_dynamics_matrix_propagates_along_edge_direction` — A -> B
   (+), seeds A only, asserts B (not A) moves at t=1. This is the test whose
   absence let the bug ship.
2. `test_isa_to_dynamics_matrix_is_transpose_of_numeric_matrix` — asserts
   `isa_to_dynamics_matrix(isa)[0] == isa_to_numeric_matrix(isa)[0].T` and
   identical `node_ids`.
3. `test_create_boolean_rules_reads_numeric_matrix_orientation_unchanged` —
   pins `create_boolean_rules`'s current (correct) reading of
   `isa_to_numeric_matrix`'s row=source/col=target orientation on a small
   A->B(+)/B->A(-) fixture, so a future "consistency" refactor cannot
   transpose that path too.

## Pre-existing test behaviour

All 48 pre-existing tests in `tests/test_dynamics.py` pass unchanged — none
needed modification, none changed behaviour. `simulate_dynamics`'s own tests
(`test_simulate_dynamics_identity_keeps_initial_state_constant`,
`test_simulate_dynamics_stable_eigenvalue_decays`,
`test_simulate_dynamics_unstable_eigenvalue_grows`,
`test_simulate_dynamics_random_initial_state_seed_reproducibility`) all use
identity or 1x1 matrices, confirmed transpose-invariant, and were left
untouched per instructions — they neither caught nor now encode the
direction bug; the new `isa_to_dynamics_matrix` tests do that instead.

No pre-existing test encoded the backwards behaviour at the ISA-matrix
boundary (there was previously no test asserting simulate_dynamics'
propagation direction against an asymmetric matrix derived from an ISA
graph), so there was nothing to report as a "quietly encoded bug" per the
task's stop-and-report clause.
